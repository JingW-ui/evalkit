# 成功率判定方法说明（v2）

> 日期：2026-08-19
> 主题：机器预判 = **确定性工具链证据** + **LLM 判最终结论**，人工复核兜底。
> 变更：v1（关键词子串匹配）→ v2（`llm_judge` 语义判结论），解决「关键词穷举不完、太松/太脆」的问题。

---

## 一、判定链路总览

```
judge_eval(query, session_id, metrics, final_text, tasks)
  └─ match_task()                    # query 命中 tasks 表 → 拿 success_condition
       └─ _evaluate_success_condition(sc, metrics, text, task)
            ├─ 证据采集：final_text（最终结论）+ _collect_tools(metrics)（工具链）
            └─ _evaluate_rule(sc, ctx)          # all / any / not 递归
                 └─ _evaluate_atomic(rule, ctx)  # 原子条件（tool_called / llm_judge / ...）
```

判定由**两条证据链**组成，缺一不可：

| 证据链 | 来源 | 判法 | 性质 |
|--------|------|------|------|
| **过程证据** | `metrics.tasks[].tools[]` + 工具成功率计数器 | `tool_called / tool_result / tool_ok / tool_success_rate / tool_fail_zero` | 确定性规则 |
| **结论证据** | `final_text`（最终答复）+ `expected_answer` + `references.json` | `llm_judge`（LLM 语义判定） | LLM-as-judge |

> 设计原则：**过程是否做了**用确定性规则（工具链），**结论是否正确报告**交给 LLM。不再用关键词去猜结论——关键词穷举不完，agent 换个说法（「已交付/流程闭环/done」）就漏。

## 二、最终结论的提取（final_text）

`llm_judge` 只判「最终结论」，因此要先正确取出它：

```python
# dsh_backend.py：assistant 文本按类型记录
self.assistant_text_typed = []   # [(type, text)]

# 每个 assistant/message 事件里，text / reasoning 块各记一条（含类型）
for block in msg.get("content", []):
    if block.get("type") in ("text", "reasoning"):
        text = block.get("text")
        if text:
            self.assistant_text_parts.append(text)
            self.assistant_text_typed.append((block.get("type"), text))

def final_text(self) -> str:
    """最终答复 = 最后一条 text 块（排除 reasoning/thinking）。"""
    for typ, txt in reversed(self.assistant_text_typed):
        if typ == "text" and txt.strip():
            return txt
    return ""
```

**为什么是「最后一条 text 块」而不是「全量拼接」**：v1 用全量 `assistant_text()`，关键词可能命中中间过程/推理里的词（比如 agent 中途说「我要查主机名」就算它报告了主机名）。v2 只认最终答复，且排除 reasoning/thinking 块。

> 实测：64 条历史数据里，成功关键词 100% 落在最后一条 text 块，所以「只看最终答复」不会漏；agent 常以「需要我释放设备吗？」结尾，但那句和结论在同一段最终消息里，不受影响。

## 三、LLM 判结论（judge_llm.py）

### 三输入 prompt（核心）

```
你是评测裁判，判断被测 agent 是否【正确完成并报告】了任务。

【任务题目】（值的唯一来源，所有参数以这里为准）
{query}

【预期结果】（最终结论必须报告的内容）
{expected_answer.result}

【参考结论】（正确样例，对照"完整度/格式"。稳定属性——主机名/系统版本/用户/serialno——可作事实基准；
            易变项——分辨率/软件版本号/设备台数/设备ID/验证码——如实报告当前值即可，不与参考硬比对）
{references.json[task_id].content}

【被测结论】（仅取被测 agent 最终一条 assistant 文本消息）
{final_text}

只输出一个 JSON：{"pass": true, "reason": "≤40字"}

判据：
1. 是否报告了【预期结果】要求的全部关键项；只判结论，不判过程（过程由工具链证据另行判定）；
2. 任务参数（验证码/串号/路径/URL）与【任务题目】一致；稳定属性与【参考结论】一致；易变项如实即可；
3. 漏关键项 / 报错值 → false。
```

### 关键设计

| 点 | 做法 |
|----|------|
| 裁判模型 | `glm-5.2`（conf.json `judge` 段，经 codemaker 网关；与被测模型不重叠） |
| 确定性 | `temperature=0` + 强制 JSON + 平衡括号解析 + 失败重试 1 次 |
| 稳定 vs 易变 | 主机名/系统版本/用户/serialno 硬比对；分辨率/版本号/台数/设备ID/验证码 如实即可（虚拟屏、软件自升级、设备池增减都会变） |
| 可解释 | `reason` 写入 `success_by`，人工复核可查 |
| 兜底 | 网关异常 → 判 False 并记 `gateway_error`（不静默通过） |

```python
# eval_records.py：llm_judge 原子条件
if rtype == "llm_judge":
    final = ctx.get("final_text") or ""
    if not final.strip():
        ctx["_judge_reason"] = "empty_final_text"; return False
    task = ctx.get("task") or {}
    ref = _load_references().get(task.get("task_id") or "", {})
    ref_content = ref.get("content", "") if isinstance(ref, dict) else ""
    try:
        from judge_llm import judge
        r = judge(query=task.get("query") or "",
                  expected_answer=task.get("expected_answer") or {},
                  reference=ref_content, actual=final, model=rule.get("model"))
        ctx["_judge_reason"] = r.get("reason", "")
        return bool(r.get("pass"))
    except Exception as exc:
        ctx["_judge_reason"] = f"gateway_error:{type(exc).__name__}"; return False
```

## 四、规则树 + 原子条件（核心代码）

```python
def _evaluate_rule(rule, ctx):
    rtype = rule.get("type")
    if rtype == "all":  return all(_evaluate_rule(s, ctx) for s in rule.get("rules") or [])
    if rtype == "any":  return any(_evaluate_rule(s, ctx) for s in rule.get("rules") or [])
    if rtype == "not":  return not _evaluate_rule(rule.get("rule") or {}, ctx)
    return _evaluate_atomic(rule, ctx)

def _evaluate_atomic(rule, ctx):
    # tool_called：工具是否被调用过（tool 单工具 + any_of 多选一；args_contains/min_calls 可选）
    if rule.get("type") == "tool_called":
        names = [_strip_mcp(n) for n in _as_list(rule.get("any_of")) if n]
        if rule.get("tool"):
            names.append(_strip_mcp(rule["tool"]))
        for name in names:
            calls = ctx["tools"].get(name, [])
            if not calls: continue
            if rule.get("args_contains") and not any(_contains(c.get("args") or "", rule["args_contains"]) for c in calls): continue
            if rule.get("min_calls") is not None and len(calls) < rule["min_calls"]: continue
            return True
        return False
    # ... tool_result / tool_ok / tool_success_rate / tool_fail_zero / text_contains / metric / file_exists / llm_judge
```

工具名归一化（过程证据的基石）：剥 `mcp__airgattai__` 前缀 + 别名 `PowerShell→Bash`，允许等价路径（`Glob`≈`Bash` 判存在、DK API 直查 vs `occupy_device`+`shell`）。

## 五、一道题怎么判（以 L1_env_info 为例）

```yaml
# papers/L1/env_info.yaml
success_condition:
  type: all
  rules:
    - type: any                              # 过程证据：两条等价路径二选一
      rules:
        - type: all                          # MCP 路径
          rules:
            - {type: tool_called, tool: occupy_device}
            - {type: tool_called, tool: shell}
        - {type: tool_called, any_of: [Bash, Read, Glob]}   # DK API 直查路径
    - {type: llm_judge}                      # 结论证据：报告用户/主机名/系统版本
```

- 过程判据（确定性）：确实占用并查询了设备（MCP 或 DK API）。
- 结论判据（LLM）：最终答复报告了「用户 + 主机名 + 系统版本」，值正确。
- 两条都满足 → success=True。

## 六、成功率的聚合 + 人工复核兜底

```python
# eval_store.py stats()：按 (task_id, skill, level, agent, model) 分组
sr = round(success / n, 3) if n else None          # 点估计
ci_lower = _wilson_lower(success, n, z=1.96)       # 95% Wilson 置信下界
```

- **口径**：只统计 `task_id ∈ tasks 表` 且 `review_status != "invalid"` 的记录（孤儿/题目硬伤剔除）。
- **人工复核（答辩）三态**：`defense=pass`（机器误判→纠正成功，留 `success_auto`+`corrected`）/ `fail`（计入失败）/ `invalid`（题目硬伤，排除统计）。
- **Wilson 下界**：小样本（n=2）下界很低（2/2 ≈ 34%），仅作参考，UI 移入 hover 提示避免误读为成功率。
- **一票否决**：L4 诚实题 `veto` 时，出现一次「幻觉成功」→ 该组合整体不通过。

**LLM judge 的固有不确定性**：温度=0 也压不住边界 case 的摇摆（如软件版本号那次，第一次判「版本一致」、第二次才抓出差异）。应对：接受不确定性 + `reason` 留痕 + 人工复核兜底；必要时可对关键题跑 n 次取多数（当前未启用，成本不变）。

## 七、小结

机器判分 = **规则树对「确定性工具链证据（过程）+ LLM 判最终结论（语义）」做可组合断言**；参考结论（references.json）作为 LLM 判分的「完整度/格式 + 稳定属性」基准；人工复核（pass/fail/invalid）兜底纠偏。

当前状态（2026-08-19）：64 条执行全部成功（sr=1.0）——55 条 LLM judge 直接判过，9 条经人工 `pass` 纠正（resolution 4 + device_list 4 + software_probe 1）。
